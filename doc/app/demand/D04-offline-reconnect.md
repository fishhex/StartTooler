## 1. 需求总览

### 1.1 背景

| 现状 | 痛点 |
|---|---|
| PC 端每 2 s 发一次 UDP 广播 | App 端用"3 个周期未收到 = 6 s"作为离线判定 |
| iOS / Android 后台会暂停 UDP 监听 | 回到前台必须重置计时，否则误判离线 |
| Wi-Fi 切换 / 飞行模式 / 路由器重启 → 广播中断 |

### 1.2 核心价值

- **稳定识别 PC 在线 / 离线**，UI 不闪烁
- **后台回前台无缝**，用户无感
- **断网后能自动恢复**

### 1.3 一句话概括

**App 端每次收到 UDP 广播刷新最后收到时间戳；连续 6 s（3 个广播周期）未刷新 → 标记该 PC 离线；App 切后台回前台立即重置计时；网络恢复后自动重新进入"已发现"状态。**

## 2. 用户场景

### 场景一：PC 正常关机

> 1. PC 关机 → UDP 广播停止
> 2. App 端 6 s 内最后一次收到广播（关机的瞬间）
> 3. 6 s 后 → 标记 PC 离线（UI 灰显）
> 4. 不提示用户弹窗（系统关机是用户行为）

### 场景二：App 切后台

> 1. 用户按 Home → App 进入后台
> 2. iOS / Android 暂停 UDP 监听（系统行为）
> 3. **不要**判定为离线——切后台是用户行为
> 4. 用户回前台 → 立即重置计时（不要让用户看到错误状态）

### 场景三：Wi-Fi 切换

> 1. 用户从家庭 WiFi 切到公司 WiFi
> 2. UDP 监听 socket 出错 / 收不到广播
> 3. 6 s 后 → 标记 PC 离线
> 4. Wi-Fi 切换稳定后 → 重新扫描，PC 在新 WiFi 中可能仍可见（如果 PC 也在新 WiFi）

### 场景四：飞行模式

> 1. 用户开飞行模式
> 2. UDP 收不到
> 3. 6 s 后 → 标记 PC 离线
> 4. 关飞行模式 → 系统网络恢复监听
> 5. 重新发现 PC

### 场景五：PC 端 HTTP 服务崩溃但进程在

> 1. PC 端 UploadServerService 异常崩溃
> 2. UDP 广播也会停（因为在同一个进程）
> 3. App 端 6 s 后判定离线

### 场景六：PC 端 HTTP 服务存活但 UDP 广播线程挂

> 1. PC 端 UDP 协程异常退出（理论不会发生，但可能）
> 2. App 端 6 s 后判定离线
> 3. PC 端实际可用（HTTP 可达）但 UDP 不发
> 4. **建议**：用户手动切换到"手动输入 IP"模式验证

## 3. 功能需求

### 3.1 离线判定阈值

| 项 | 值 | 说明 |
|---|---|---|
| 离线阈值 | **6 秒** | 3 个 UDP 广播周期（每 2 s 一次）|
| 计算方式 | `now - lastReceivedAt > 6000ms` | 严格按"3 次未收到" |
| 实现位置 | 每台 PC 一个 `lastReceivedAt` 时间戳 | 不全局计时 |

### 3.2 状态定义

每台 PC 在 App 端有 3 个状态：

| 状态 | 触发 | UI |
|---|---|---|
| 在线（Online） | 最近 6 s 内收到广播 | 正常颜色 / 可点 |
| 离线（Offline） | 6 s 未收到广播 | 灰显 / 不可点 |
| 未知（Unknown） | 首次发现，未确认可达 | 半透明 / "验证中..." |

### 3.3 状态转移

```
   ┌────────┐  收到广播    ┌────────┐
   │  未知   │ ──────────→ │  在线   │
   └────────┘              └────────┘
        ▲                        │
        │                        │ 6 s 未收到
        │                        ▼
        │                  ┌────────┐
        └────── 收到广播 ── │  离线   │
                            └────────┘
```

### 3.4 后台回前台

| App 端状态 | 处理 |
|---|---|
| App 切后台 | 暂停离线计时器（iOS / Android 系统会停 UDP，本就不该判定） |
| App 回到前台 | 立即重置该 PC 的 `lastReceivedAt = now` |
| 回到前台后第一次扫描 | 立即触发 UDP 监听；如 3 s 内收到广播 → 标记在线 |
| 回到前台后 6 s 仍未收到 | 标记离线（之前已离线的） |

### 3.5 网络恢复自动重连

| 网络事件 | 处理 |
|---|---|
| 网络从无到有（Wi-Fi 重连 / 飞行模式关闭）| 触发重新扫描 |
| 网络从 A Wi-Fi 切到 B Wi-Fi | 重置所有 PC 状态为"未知"，重新发现 |
| 网络断开（飞行模式 / 全部断开）| 标记所有 PC 离线 |

实现建议：监听平台网络可达性事件（iOS `NWPathMonitor` / Android `ConnectivityManager.NetworkCallback`）。

### 3.6 探活用 health

UDP 不可靠时，应用 HTTP `GET /api/v1/health` 二次验证：

| 场景 | 行为 |
|---|---|
| UDP 收到但 health 失败 | 标记为"UDP 收到但 HTTP 不可达"——可能 PC 端 HTTP 进程挂了；UI 标灰 |
| UDP 未收到但 health 成功（用持久化 IP）| 标记为"HTTP 可达但 UDP 收不到"——可能 UDP 线程挂；UI 显示但说明"UDP 异常" |
| UDP 未收到且 health 失败 | 确认离线 |

### 3.7 不做"主观"超时

不要使用：

- ❌ 5 s 收不到就提示"扫描中..."（用户感知级 UX 节奏）
- ❌ 30 s 收不到就完全退出扫描页（应等到用户主动切）
- ❌ 1 分钟未用就关闭 socket（应保持监听）

详见 [D06](D06-error-handling.md) 关于用户感知 vs 技术超时的区分。

## 4. 非功能需求

| 维度 | 要求 |
|---|---|
| 状态切换 UI 响应延迟 | ≤ 500 ms |
| 离线判定误差 | ±500 ms（不要更精确，UDP 本身不可靠） |
| 后台计时器资源占用 | 0（直接靠前台监听维持，不开定时器） |
| 网络事件监听资源 | 平台原生 API（`NWPathMonitor` / `NetworkCallback`），不轮询 |

## 5. 边界情况

| 场景 | 处理 |
|---|---|
| PC 端正常关机 | 6 s 后离线（不弹窗） |
| PC 端断电（瞬断） | 6 s 后离线 |
| App 切后台 1 小时 | 回前台立即重置计时，重新发现 |
| 飞行模式开关 | 网络事件触发重新发现 |
| 路由器重启（DHCP 重发） | PC 端 IP 可能变；App 端按 `name+port` 重新匹配 |
| UDP 收不到但 HTTP 可达 | 标灰并说明"UDP 异常，请检查 PC 端星助" |
| UDP 收得到但 HTTP 不可达 | 标灰并说明"HTTP 异常" |
| 路由器 AP 隔离 | UDP 收不到 + HTTP 也不可达；走手动输入兜底 |
| PC 端切换 Wi-Fi（IP 变） | App 端重新发现；按 `name+port` 识别 |

---

## 6. 不做清单

| 内容 | 理由 |
|---|---|
| 后台持续网络监听 | 系统限制 |
| 心跳 / ping-pong | UDP 广播已每 2 s 一次 |
| TCP keepalive | 走 HTTP，已有超时 |
| 复杂的网络质量评分 | 单次失败重试一次即可 |

---

## 7. 验收标准

- [ ] PC 启动 HTTP 服务 → App 1-2 s 内出现设备（在线）
- [ ] PC 关闭 HTTP 服务 → App 6 s 内标灰离线
- [ ] App 切后台 → 立刻暂停离线判定；回前台立即重置
- [ ] 切 Wi-Fi → 飞行 → 恢复 Wi-Fi，App 能自动重新发现
- [ ] UDP 收不到但 health 200 → 提示"UDP 异常"
- [ ] UDP 收得到但 health 失败 → 标灰
- [ ] 多 PC 同 LAN：某台关 → 仅该台标灰
- [ ] 网络恢复事件触发扫描（不依赖 App 重启）
